## Flight, defense and input

The ship combines pitch/yaw, coupled banking, throttle and lateral/vertical movement. The Phoenix drives a simulated collision body through the installed ShipCore thruster and gyro components; native code translates forward/strafe target velocity into bounded thrust and angular rate into rate-damped gyro acceleration. The adapter uses exponential velocity-error response and disables the vendor zero-velocity dampener, which otherwise applies full braking at zero cruise trim. Thrusters tick after the pawn command and before physics. Banking targets an attitude so a held turn does not continuously roll. Upgraded acceleration/response remain inputs to that adapter, and `GetVelocity` reports actual physics velocity. The classic hull retains exponential response and acceleration limits integrated through bounded substeps with swept collision. Accepted domain boost changes target speed; raw boost input cannot add thrust after the resource rule rejects it.

The owner-approved follow-up replaces the automatic minimum cruise with explicit 0–1 throttle. Right trigger supplies analog power; W/S raises/lowers a persistent keyboard setting at 0.5 per second. Possession changes reset keyboard throttle, and takeoff finishes at zero power. With throttle released, `FlightVelocityTarget` retains world-space momentum even when the hull turns; an explicitly commanded lateral/vertical axis still uses its maneuvering thrusters. Accepted boost uses full engine power and the existing boost multiplier/resource rules. Accepted brake requests zero target velocity, suppresses boost and retains its outside-station heat limit; inside the 180 m station zone it can stop without overheating. Engine sound and main exhaust follow actual power, with the controlled docking/lift sequence retaining its small lift effect. These semantics apply to both hull adapters and supersede the old minimum-speed/station-trim behavior.

Throttle ownership is independent of the last input device used for HUD prompts. Fresh W/S presses select the keyboard setting; RT presses, releases and adjustments exceeding one percent from the last command select analog power. Smaller samples accumulate toward that threshold, so gradual deliberate adjustment still works. Looking, firing or switching menu devices cannot revive a retained keyboard setting after RT release. Possession resets ownership and both stored throttle values.

Dodge adds directional velocity and never grants invulnerability. `ReceiveImpact` applies a one-time velocity impulse in cm/s; continuous gravity remains acceleration integrated over time. Relative swept contact supplies the closest-contact normal, so a fast crossing does not deflect toward the wrong side using the end-of-frame position. Contact regressions cover frame-rate agreement and crossed-contact direction.

Shield absorbs first and has no automatic recharge. Hull can recover fully, with delay and different safe/danger rates. Lightweight damage-type effects and temporary effective-tier impairment preserve purchased upgrade tiers. Automated adapters verify boost/brake motion, dodge collision damage and manual weapon impacts; domain tests cover the resource rules. Natural overlapping contacts/forces, contextual recovery and feel still need gameplay verification.

Manual aim traces from the camera through the actual projected HUD reticle and converges from `MuzzleWorldPosition`. The Phoenix uses its authored gun-arrow transforms; fitted classic weapon modules retain their mount, with a measured nose/height fallback when either presentation source is absent. Camera hits at/behind the muzzle's forward plane cannot reverse a shot. Soft targeting measures its cone from that same camera ray, rechecks range and muzzle cover when firing, and tapers assistance from the cone edge to a default 20% maximum (hard-clamped to 40%). It does not rotate the ship. Rapid Laser traces native damage over `WeaponRange` (14000 cm by default), confirms damageable hits immediately and clips its zero-damage visual tracer to the obstruction; Heavy Cannon retains its 19000 cm/s physical projectile. Neither weapon fires while moored, docking or taking off. Camera arm, height, pitch and reticle offset come from the selected hull definition; boost pullback/FOV adaptation remains.

Both player projectile paths retain configured maximum travel. The final sweep is clipped to remaining range and lifetime, preventing a long frame from hitting beyond either bound. Enemy shots test relative projectile/ship translation over that same live interval against the Phoenix's current compound hull pose, or the classic hull's original sphere. The first contact is compared against the first eligible world obstruction; earlier cover, including an equal-time tie, blocks damage. Ship-position history is seeded at launch, a tick prerequisite follows the tracked ship, and all world bodies evaluate in PostPhysics so both swept paths use completed movement from the same frame. Tracking changes reset history/prerequisites together. Hazard impact applies its mass-independent additive velocity change immediately so the next thrust calculation sees the impacted velocity. Solid hazards and enemies use the same compound contact query with their existing 1.1-second domain cooldown; their rigid-body callback cannot add a second generic impact charge. These relative sweeps cover translation between frames, not continuously changing angular poses. Six seconds remains a lifetime ceiling, not extra weapon range. Effective weapon/buff scaling is applied once. Regressions cover camera-reticle convergence, muzzle obstruction, native weapon damage, measured engine contact, empty space and cover ordering; physical aiming and rendered framing remain separate acceptance checks.

PlayerController resets toggle latches and keyboard throttle when possession changes. Flight uses RT throttle, B boost, LT brake and RB fire; on foot, Space/A jumps and E/Y interacts. Flight docking still uses E/A, and menu confirmation uses Enter/A. Positive raw MouseY and right-stick Y both mean up; the saved pitch inversion applies once before either the flight body or walking view consumes that command. Unreal's viewport already converts upward screen movement to positive MouseY. Separate mouse/controller sensitivities remain adjustable from 0.3–2.9. ## Local save protocol

| Slot | Payload | Behavior |
| --- | --- | --- |
| `SS_Account_v1` | ACCOUNT v2; reads v1 | Progression, tutorial flags, summary, awarded ID and bounded history |
| `SS_Settings_v1` | SETTINGS v1 | Audio, controls, accessibility and graphics preferences |
| `SS_Suspend_v1` | RUN v1 | Active station run, build/meters/counters, contract/flags, pending reward and domain RNG |

The Unreal envelope remains version 1. Strict codecs reject malformed, oversized, nonfinite, out-of-range, trailing and inconsistent data without changing the destination. Account v1 migration preserves available fields and leaves new history empty rather than inventing details.

`WriteDomain` uses Unreal's `SaveGameToMemory`, the same serialization used by `SaveGameToSlot`, and checks the deserialized envelope version, validity and payload before storage. Existing saves remain compatible: all three slot names, payload versions and envelope version are unchanged. Reads still use Unreal's generic SaveGame backend.

`SSLocalSave` accepts only those three slots on the game thread under Windows, and only when the active platform backend is the engine's exact generic singleton. Configured alternative backends fail closed. It maps `ProjectSavedDir/SaveGames/<slot>.sav` through the platform file layer, including the external write path used for the native replacement.

Each write creates a unique `<slot>.sav.<GUID>.tmp` beside the destination. It writes the serialized bytes, calls `Flush(true)`, closes the handle, reloads the staging file and compares every byte. The installed Windows file handle uses `FlushFileBuffers`; see Microsoft's [FlushFileBuffers documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers), updated 2021-10-13. Only verified staging bytes proceed to `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`. There is no pre-delete of the live slot and no `MOVEFILE_COPY_ALLOWED` fallback; source and destination are in the same directory for a same-volume replacement. See Microsoft's [MoveFileExW flag documentation](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), updated 2023-06-01.

Staging/verification/replacement failure returns an error and attempts to delete only that temporary file. A process interruption or failed cleanup can leave an orphan `.tmp`; it is neither loaded as a `.sav` slot nor automatically promoted. Successful replacement is the write acknowledgement. There is no later live-file read that could report a transient failure after the action already committed.

Suspension persists account/settings before the run. Resume validates a candidate, replaces the suspended slot with a consumed tombstone, and exposes the candidate only after replacement succeeds. Death persists account/run identity before invalidating suspension; failed persistence blocks restart. Latest/retained awarded IDs exclude stale completed suspensions. Unreadable accounts are protected from overwrite. At Station 2, discard persists highest-wave progression, then invalidates suspension, then clears the run. A failed write preserves live state; account-first ordering and max-preserving resume prevent a later older checkpoint from downgrading the record. No death XP or history is fabricated.

This protects the live file from truncation during staging; it does not provide an atomic transaction across slots, an unlimited anti-replay ledger, automatic backups or cloud conflict handling.
