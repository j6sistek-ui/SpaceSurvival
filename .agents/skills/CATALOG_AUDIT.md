## Practical proposal and usage discipline

1. **Make real controls and combat the first acceptance workstream.** Start with the live reward/device asymmetry identified in the issue, then normal flight/camera/dodge/weapon behavior and station controls. Define expected input and response before editing. A physical comfort decision needs the owner's play experience; agents can still reproduce state routing, instrument behavior and fix discovered defects.
2. **Develop the player feedback together with the mechanic.** For a bounded encounter or interaction, review warning timing, visible effect, collision/damage, sound, HUD result and cleanup as one path. Prioritize existing two-enemy/four-hazard readability, not more content. Use normal Waves 1-10, both climaxes and stations to expose overlap and pacing weaknesses.
3. **Give character motion and presentation their own acceptance work.** Continuous pilot/exit/walk motion, silhouette/camera clearance, texture/material correctness and layered sound need explicit evidence. Asset import and still screenshots do not close these requirements.
4. **Fix architecture where it obstructs that work.** Review lifetimes, data knobs, asset residency, menu ownership and save latency as their paths are touched. Keep the durable domain and scoped roster. Large framework migrations need a concrete benefit and a bounded experiment first.
5. **Produce a reproducible current-package evidence set.** Separate deterministic engine tests, natural play, physical devices, listening, rendered readability, CPU/GPU/memory traces and clean-PC delivery. Record source/package/settings/assistance once and update stale playtest steps. Do not substitute historical high-end fixture numbers for the current 60 FPS requirement.

For each implementation task, use one player-visible goal, one primary skill and at most a small number of relevant references. Check the engine signatures actually used; batch coherent edits before a build; repeat expensive validation only when changes or failures justify it. One integration lead owns the editor and package. Specialist review can run in parallel on isolated source questions, but parallel editor mutations and uncoordinated game architecture changes waste work.

The proposed repository delivery is **nine discoverable workflows: eight adapted MIT UnrealXu skills plus one original SpaceSurvival gameplay-review skill**. A separate original work-area guide links the broader Buckley knowledge on demand, and this document records every inclusion/omission. Nine folders is a packaging choice, not a nine-domain ceiling. Buckley's raw skill bodies are not vendored because an explicit redistribution grant was not identified at the pinned revision. Licensing remains unconfirmed; do not invent permission or imply wrongdoing. The project can use the linked guidance and independently written project instructions.

MCP remains a separate tooling experiment. First inspect and trial the installed UE 5.8 native MCP on one bounded read/inspect/edit/readback task at an integration checkpoint. Evaluate VibeUE's UE5.8 extension only if it closes an actual tool gap. Skill files alone do not create an editor connection. No MCP installation/activation or editor restart is included in this guidance PR. Measure successful task completion, corrections, tool failures and usage on comparable tasks; neither catalog provides proof of a guaranteed usage reduction for this game.
